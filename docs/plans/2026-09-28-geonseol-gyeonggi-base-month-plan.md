# 건설경기 인식 지수 — 기준월 선택·회차 연동 작업 계획

**작성일**: 2026-09-28
**근거**: [정책](./2026-09-28-geonseol-gyeonggi-policy.md) §5, [구현 계획](./2026-09-28-geonseol-gyeonggi-impl-plan.md)
**상태**: 완료 (2026-09-28). §2의 질문은 모두 제안대로 확정했다. 결과는 §7.

## 0. 요구

1. 기준월을 사용자가 바꿀 수 있어야 한다.
2. 기본 기준월은 **보고월 − 2개월**이다. 오늘(9월)이 보고월이면 7월, 8월을 보고월로 보면 6월이다.
3. 자금수지표를 올리면 그 회차에 연동된다. 이전 회차 7월, 최신 회차 8월을 올리면 보고월은 8월이고, 기준월은 6월이다.

## 1. 지금 규칙과의 관계 — 정책 §5를 바꾼다

| | 지금 (정책 §5) | 바뀐 뒤 |
|---|---|---|
| 기준월을 정하는 것 | **데이터**. 지표별 최신월 중 가장 이른 달 | **달력**. 보고월 − 2개월, 사용자가 바꿀 수 있음 |
| 보고월 | 없음 | 최신 회차의 기준월. 회차가 없으면 오늘이 속한 달 |
| 오늘(9/28) 결과 | 7월 (ECOS가 7월까지 있어서) | 7월 (9월 − 2) — 우연히 같다 |
| 8월 회차를 올리면 | 7월 (회차와 무관) | **6월** |

지켜야 할 기존 결정:
- **거슬러 내려가지 않는다(정책 Q2).** 고른 달에 값이 없으면 이전 달로 옮기지 않고 산출불가를 낸다. 이 원칙은 그대로 유효하다. 기준월을 사람이 정하므로 오히려 더 분명해진다.
- **결측은 0이 아니다.** 그대로다.

새로 생기는 경우:
- **고른 달이 아직 공표 전일 수 있다.** 예를 들어 9월 3일에는 7월 건설 통계가 아직 없을 수 있다. 데이터 기준 규칙에서는 생기지 않던 일이다. 이때는 산출불가로 두되, 사유를 "값이 없습니다"가 아니라 **"아직 공표 전입니다(ECOS 최신 2026/06)"** 로 구분해 보인다. 빠진 것과 아직 안 나온 것은 조치가 다르다.
- **과거 달을 보면 지금의 ECOS 값으로 계산된다.** 6월 기준을 다시 보면 그동안 수정된 잠정치·기준연도 개편이 반영된 값이 나온다. 그때 보고한 숫자와 다를 수 있다(정책 §6-2, 구현 계획 R1). 화면에 이 점을 한 줄로 알린다.

## 2. 정한 것 (2026-09-28, 모두 제안대로)

| # | 질문 | 제안 |
|---|---|---|
| B-Q1 | 연동 대상은 **회차 기준월**인가, 화면에서 사용자가 바꾼 **자금수지표 기준월 선택**인가. 지금 화면에는 유동성 Gap·적정 시재용 기준월 선택이 따로 있다 | **회차 기준월**. 자금수지표 기준월 선택은 계획 달(9·10월…)까지 고를 수 있어서, 따라가면 건설경기 기준월이 아직 공표 전인 달로 밀린다. 건설경기는 자기 선택 상자를 따로 둔다 |
| B-Q2 | 사용자가 고르는 것은 **보고월**인가 **기준월**인가 | **기준월**을 직접 고른다. 기본값만 보고월 − 2로 채운다. 화면에 "보고월 8월 → 기준월 6월"을 함께 적는다 |
| B-Q3 | 고를 수 있는 범위 | 2016/03(분양회수 이력이 되는 첫 달)부터 오늘 − 1개월까지. 범위 안이라도 값이 없으면 산출불가다 |
| B-Q4 | "2개월"은 고정 정책인가 | 정책 상수(`보고 시차 = 2개월`)로 한 곳에 둔다. 바뀌면 그 값만 고친다 |

## 3. 설계

### 3-1. 도메인

- `policy.ts`에 `REPORT_LAG_MONTHS = 2`를 둔다. 정책 문서 §5를 이 규칙으로 고친다.
- `construction-perception.ts`
  - `defaultBaseMonth(reportMonth) = reportMonth − 2`
  - `assessLatest`와 `baseMonthOf`(데이터 기준 규칙)는 **지운다.** 기준월 규칙이 두 벌이면 어긋난다. 지표별 최신월은 진단 정보로만 남긴다.
  - 기준월 하나를 받는 `assessConstructionPerception(input, month)`는 그대로 쓴다.

### 3-2. 유스케이스 (`application/construction-perception.ts`)

```ts
assessPerception(source, repo, request: { baseMonth?: YearMonth; reportMonth?: YearMonth }, now)
```

- 기준월을 정하는 순서: `baseMonth`가 있으면 그 달 → 없으면 `reportMonth − 2` → 둘 다 없으면 `오늘이 속한 달 − 2`.
- 결과에 `reportMonth`와 `baseMonth`, 그리고 기준월이 어디서 왔는지(`선택` / `회차` / `오늘`)를 싣는다. 화면이 설명 문장을 만들 때 쓴다.
- 결측 사유를 다듬는다. 기준월(또는 비교 월)이 그 지표의 최신월보다 뒤면 "아직 공표 전입니다(최신 YYYY/MM)", 아니면 지금처럼 "값이 없습니다".

### 3-3. 라우트

- `GET /api/construction-perception?baseMonth=2026/06&reportMonth=2026/08`
- 두 인자 모두 없어도 된다. 형식이 틀리면 400이다. 검증은 `parseYearMonth`로 한다.

### 3-4. 화면

- **보고월**: 최신 회차가 읽혔으면 `calendarOf(latest, latest.defaultBaseMonth)`, 아니면 없음(서버가 오늘로 정한다).
- **기준월 선택 상자**: 건설경기 카드 안에 따로 둔다(B-Q1). 기본값은 보고월 − 2.
  - 회차를 새로 올리면 선택을 기본값으로 되돌린다. 8월 회차를 올리면 6월로 돌아간다.
  - 사용자가 바꾼 달은 요청의 `baseMonth`로 보낸다.
- **설명 한 줄**
  - 회차 연동일 때: "보고월 2026/08(최신 회차) → 기준월 2026/06"
  - 회차가 없을 때: "보고월 2026/09(오늘) → 기준월 2026/07"
  - 사용자가 바꿨을 때: "직접 고른 기준월 2026/05"
- 과거 달을 볼 때 알림 한 줄: "ECOS 현재 값으로 계산합니다. 당시 보고한 값과 다를 수 있습니다."
- 기존 `baseMonthNote`("주택매매가격지수·환율·주가는 2026/08까지 나왔지만…")는 이제 맞지 않는 설명이라 지운다. 대신 지표별 최신월을 공표 전 사유와 함께 보인다.

### 3-5. 호출 횟수

기준월을 바꿀 때마다 ECOS 9건을 다시 부르게 된다. ACL에 **짧은 메모리 캐시(10분)** 를 둔다. ECOS 계열은 달이 바뀌어도 같은 전체 계열이라 기준월과 무관하게 재사용할 수 있다. 캐시는 서버 프로세스 안에만 있고 키가 바깥으로 나가지 않는다.

## 5. 확인할 것 (B6)

- 회차 없이 열면 기준월 2026/07, 결과가 지금과 같다(15.15, 정상).
- 8월 회차를 올리면 기준월이 2026/06으로 바뀌고 설명이 "보고월 2026/08(최신 회차) → 기준월 2026/06"이다. 6월 값은 엑셀과 비교할 수 있다. 엑셀 2026/06은 13.42 정상이지만, ECOS 수정값으로는 다를 수 있다(R1).
- 선택 상자에서 2026/05를 고르면 5월로 산출된다. 다시 회차를 올리면 기본값으로 돌아간다.
- 2026/08을 고르면 공표 전 지표가 사유와 함께 산출불가로 나온다.
- 기준월을 여러 번 바꿔도 ECOS 호출이 10분 안에 한 번뿐이다(서버 로그).
